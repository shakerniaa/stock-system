This file exists so a fresh Claude Code session (on another machine, or after a context reset) can pick up this project without re-deriving everything from scratch. Read this, then `stocksystem-dev-kit/CLAUDE.md` and `stocksystem-dev-kit/DECISIONS-v1.1.md` (the binding spec — overrides the `.dc.html` design files wherever they conflict).

## Post-build QA: real catalog + first end-to-end test of the configurator

Everything above was built against an almost-empty catalog (one simple test product), so whole code paths had never actually run. `dev-tools/seed-catalog.php` (run from the WP root: `wp eval-file <repo>/dev-tools/seed-catalog.php`; idempotent) now seeds the design's real six categories (`stocksystem_nav_categories()` fallback list), the five brands, and 9 products covering every card state — on sale, low stock, out of stock, featured, clearance, free shipping, bestseller, real product photos from the dev kit, test-report meta, A/B grades — plus one **variable** RAM/storage product with add-ons. Seeding it immediately surfaced real bugs in the configurator, a headline feature that had never been exercised:

- **Fatal error on every variable product page** — `inc/product-configurator.php` called `$product->get_attribute_object()`, which doesn't exist on `WC_Product`. Now looks the attribute up from `$product->get_attributes()`.
- **Tiles changed the hidden `<select>`s but price/stock/add-to-cart never appeared** — WooCommerce's `add-to-cart-variation.js` finds attribute fields with `$form.find('.variations select')`; our hidden-select wrapper in `variable.php` lacked the `variations` class, so `wc_variation_form()` bound to zero fields and no `found_variation` ever fired. Added the class (commented in the template — it's load-bearing).
- **Add-on surcharge silently never applied** — `stocksystem_add_addons_to_cart_item_data()` used `wp_list_pluck($addons, null, 'id')`, which can't take a null field (logs "Undefined array key", returns nulls), so no chosen add-on ever matched. Replaced with `array_column($addons, null, 'id')`. Verified: 8GB/256GB (28.5M) + Windows licence (1.2M) → cart shows the add-on line and 29.7M total.
- **Hardening**: the two admin JSON save handlers (`_addons` in `inc/product-addons.php`, category `faq_json` in `inc/term-meta-fields.php`) now `wp_json_encode(..., JSON_UNESCAPED_UNICODE)` so Persian stores as real text, not `\uXXXX`. Discovered because the **SQLite dev database (this Mac only) mangles `\u` escape sequences on write** (`ل` → `u0644`, backslash lost) — a dev-environment quirk, not something MySQL would do, but unescaped storage is more robust and human-readable anyway. If Persian JSON ever looks like `u0644u0627…` on the SQLite site, that's the cause.
- Seeding gotcha, for anyone editing the script: under `wp eval-file`, top-level variables aren't reachable from functions via `global` (everything must be passed as parameters), and variation attribute keys must be the full taxonomy name (`pa_ram`, not `ram`) or WooCommerce saves empty values.

## Bugs found and fixed along the way

- **Customizer defaults never reached the front end.** `stocksystem_business()` called `get_theme_mod($key)` without a `$default` argument — a Customizer `'default'` only applies inside the Customizer preview, never on the real site. Fixed by centralizing key/default/label in `stocksystem_business_settings()` and passing the default through. This was invisible until we actually had a live site to look at — worth remembering that Customizer defaults always need the explicit second argument.
- **Store currency was never configured** — fresh WooCommerce defaults to USD/2-decimals, so `wc_price()`-based rendering (cart totals, order review, thank-you page — anywhere using native WC price functions rather than `stocksystem_format_number()`) showed `$32900000.00` instead of Toman. Fixed in `inc/woocommerce.php`: currency seeded to `IRR` on activation (WooCommerce has no native "Toman" code — standard Iranian-store convention is IRR with the symbol overridden to "تومان" via `woocommerce_currency_symbol`, entering prices directly in Toman units) with 0 decimals and the `٬` thousands separator as the *actual* option value (not just a hard filter — admin can still change it).
- **WooCommerce's radio-type form field renders an extra plain `<label>`** for the field's own title (pointing at the first option), before the real per-option `label.radio` elements — a blanket `.invoice-type-field label` CSS selector styled all three as pills. Fixed by scoping to `label.radio` only and marking the field `required` (it always has a default, so this also removes WC's auto-appended "(اختیاری)" suffix it adds to non-required field labels).
- **`[hidden]` + an author CSS rule setting `display: flex/grid`** on the same element silently un-hides it — author styles always beat the browser's own `[hidden] { display: none }` UA rule, regardless of selector specificity. Hit this on the OTP code-entry step and the password-login toggle (both showed immediately instead of staying hidden). Every element that's toggled via the `hidden` attribute needs an explicit `.selector[hidden] { display: none; }` rule alongside whatever `display` value it uses when shown — grep the theme for `[hidden]` in the CSS files before adding a new toggled element, the existing ones (mega menu, mini-cart, mobile drawer, search suggestions) already do this correctly and are the pattern to copy.
- **`wc_create_new_customer()` doesn't accept a `display_name` arg**, and WooCommerce's own account-details save handler requires `account_display_name` to be present in `$_POST` directly — it does *not* fall back to the user's existing value the way the code reads at first glance. Both silently produced accounts with an empty display name / a hard "required field" error on save. Fixed by setting `display_name` via a separate `wp_update_user()` call at creation time, and by backfilling `$_POST['account_display_name']` (from first+last name) and `$_POST['account_email']` (from the existing address, since real email is optional for an OTP account) in a `wp_loaded` hook that runs *before* WooCommerce's own handler — see `stocksystem_backfill_account_details_post()` in `inc/otp-auth.php`. Same lesson as above: WooCommerce's "required field" checks are often a direct `empty($_POST[...])` test, not a check against the field's actual current value, so a customized form that drops or renames a field needs to backfill `$_POST` before WooCommerce's handler runs (hooked at `wp_loaded` priority 20 — hook earlier).

## A real infrastructure trap: WooCommerce defaults to block-based Cart/Checkout

Recent WooCommerce (11.x) creates the Cart/Checkout pages with `<!-- wp:woocommerce/cart -->` / `<!-- wp:woocommerce/checkout -->` **blocks**, not the classic `[woocommerce_cart]`/`[woocommerce_checkout]` shortcodes. Blocks completely bypass `woocommerce/cart/cart.php` and `woocommerce/checkout/form-checkout.php` template overrides — CLAUDE.md's whole "override the corresponding WooCommerce template" approach (and everything built in this session) assumes the classic system. **Fix applied**: the Cart and Checkout pages' `post_content` were switched to the plain shortcodes. If you ever recreate these pages (or set up a fresh site), check `post_content` on `wc_get_page_id('cart')`/`wc_get_page_id('checkout')` first — if it contains `wp:woocommerce/cart` or `wp:woocommerce/checkout`, swap it for the shortcode before assuming a template override isn't working.

Two other fresh-WooCommerce-install traps hit during this session, worth knowing up front next time:
- **"Coming soon" mode** (`woocommerce_coming_soon` option, WC's "Launch Your Store" feature) shows a gate page on the entire front end until turned off — looks exactly like a broken theme/template if you don't know it exists. `update_option('woocommerce_coming_soon', 'no')`.
- **Iran isn't missing from the country dropdown** — it's just alphabetized under its Persian name (ایران) once the locale is `fa_IR`, so searching "Iran" in the select2 box finds nothing. Not a selling-location restriction (`woocommerce_allowed_countries` is `all` by default).
